Clearing each cache for real

Ulaa / any Chromium browser
  chrome://net-internals/#dns  → Clear host cache
  chrome://net-internals/#sockets → Flush socket pools
  (a Chromium fork may also answer on ulaa://net-internals/#dns)

Windows
  ipconfig /flushdns
  ipconfig /displaydns

Linux with systemd-resolved
  resolvectl flush-caches
  resolvectl statistics
  resolvectl query mail.zoho.in

macOS
  sudo dscacheutil -flushcache
  sudo killall -HUP mDNSResponder

Recursive resolver (if it is yours)
  rndc flush            # BIND
  unbound-control flush mail.zoho.in

Order matters when you are debugging: clear the browser cache first, then the OS one. Flushing only the OS cache while Ulaa still holds the old address changes nothing for that tab.

Check the real chain yourself

dig +trace mail.zoho.in        # every referral, root downwards
dig NS in.                     # who serves the .in zone
dig NS zoho.in                 # Zoho's authoritative servers
dig mail.zoho.in +noall +answer   # the record and its TTL
dig mail.zoho.in @8.8.8.8      # ask one resolver directly

# run it twice, a second apart, and watch the TTL fall:
dig mail.zoho.in +noall +answer; sleep 1; dig mail.zoho.in +noall +answer

nslookup mail.zoho.in          # Windows equivalent

The addresses and nameserver names in this animation are illustrative. The TTL you see falling in a real dig is the resolver telling you how much of its own countdown is left — which is exactly what your OS then copies into its cache.
